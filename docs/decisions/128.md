# 128. cartouche.cloud is Cartouche's domain, and its DNS records are kept in the repository

2026-11-17

The owner registered `cartouche.cloud` at OVH and put its zone at Cloudflare, in their account, and handed it to the project. The zone's records are [`domain/records.json`](../../domain/records.json), each with why it is there, and the [Domain](../../.github/workflows/domain.yml) workflow applies the file from main, in one batch, with an account token of Cloudflare's limited to the zone's DNS (`CLOUDFLARE_DOMAIN_TOKEN`, environment `cloudflare`). It changes only the records it made, marked in their comments, and leaves the zone's others as they are; a change is a pull request on the file, which the CI tests ([domain/README.md](../../domain/README.md)). The first records point the apex and `www` to GitHub Pages, every one *DNS only*, with nothing else at the apex and no wildcard, so that the showcase site moves to `https://cartouche.cloud` once its `CNAME` file follows; and SPF and DMARC say that no server sends mail as the domain.

**Why.** The owner asked the project to take the domain in hand (2026-11-17). A file in the repository is reviewed in pull requests, tested and applied by the CI, as the telemetry's server is deployed (43): nobody changes the zone by hand, and the token stays in GitHub's secrets, limited to this zone. GitHub Pages stays the site's host, as decision 40 put it there: free, its workflow unchanged, the old address sent on to the new one by GitHub itself. Behind Cloudflare's proxy, GitHub Pages could not get the site's certificate, and another record at the apex would stop it too. The domain sends no mail, and without SPF and DMARC anyone could send mail that claims to come from it. The site still names no server of the project (40): DNS records are public by nature, and say only where the site is.
