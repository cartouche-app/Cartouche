# 134. A sign-in asks Apple once for a new anisette machine, and Cartouche tells Apple's refusals in English in its own words

2026-11-18

A sign-in that needs a new anisette machine provisions it from the iPhone straight to Apple (gsa.apple.com: its lookup, then the start and the finish of the provisioning), whichever of the Cartouche Installer's anisette servers signs it. When Apple answers one of those steps with an HTTP error, or with an answer AnisetteKit cannot read, the sign-in ends there, as the Cartouche Installer's does, which asks one server: the built-in SideStore no longer goes on with the next server, which would only send Apple the same requests from the same iPhone ([patch 0024](../../app/patches/sidestore/0024-ask-apple-once-for-a-new-machine-and-say-what-it-answered.patch)). Apple's answer is told by AnisetteKit's words, which name the step; a server that does not answer, or whose own answer cannot be read, still hands on to the next. This narrows [decision 57](../decisions.md), whose sign-in went on with the next server on any error.

Apple's refusal for now, an HTTP 4xx other than its 429, is the cause `provisioningRefused`: Cartouche says, in its own words, that Apple refuses for now to set up a new sign-in on this iPhone, before the Apple ID is even sent, and keeps the player from signing in again for as long as after Apple's limits, counted in a row with them ([`CartoucheSignInPause`](../../launcher/Sources/CartoucheSignInMessage.swift)): 15 minutes, then 30, 60 and 120. Its 429 is Apple's limit (`tooManyAttempts`), any other answer one of Apple's that could not be read. Two more of Apple's answers that the built-in SideStore passes on in English, with its code, are told in Cartouche's words, without a wait: the sign-in's session has expired (1100), to sign in again and type the code Apple sends if it asks for one; and Apple refuses the sign-in without a reason (-22405), to wait a few hours, sign in again once, then see on account.apple.com, in Safari, whether the Apple ID needs anything, should Apple still refuse the next day. The measurements send Apple's answer to a new machine with its status (`http`), `service` `provisioning`, and the step that gave it (`reason`: `lookup`, `start`, `finish`).

**Why.** In a player's report, sign-ins that never went through, with Cartouche installed and its pairing in place, ended on "Your session has expired. Please log in. (1100)", then on "HTTP error (401): Apple PTM/TK endpoint returned HTTP 401", the finish of the provisioning, and on "This Action Cannot Be Completed (-22405)", each shown as it came, in English. Each sign-in that ended on the 401 had gone through the four servers in a few seconds, each of which asks Apple for the machine from the iPhone: up to twelve times for three sign-ins in a row. The last server asked, which had given the anisette of the sign-in a minute before, got Apple's 401 too, and a new machine went through again some forty minutes later, through the same servers in the same order: Apple refusing new machines from that iPhone for a while, which more requests can only make last, more than a server at fault. AnisetteKit gives the same error, an answer it could not read, for headers missing from a server's answer, which names none of Apple's steps: that one stays the server's. 1100 and -22405 are Apple's own codes for the account, with a machine it had accepted, not the anisette's. None of this was tried on an iPhone.
