# 123. Behind the console, the game's process asks for the keyboard, without showing one, so that its controllers reach it

2026-11-17

Behind the console, iOS hands a controller's presses to the process that has the keyboard, as it hands it a hardware keyboard's keys, and LiveContainer's scene hosting gives the keyboard to the game's process only when the game asks for it or the player touches the game's screen. While the game's scene is active, Cartouche's part of the game's process now asks for it as a text field does: a view of its own in the game's window, which takes text and becomes the first responder, with an empty view of no height in the keyboard's place. No keyboard shows, no bar of shortcuts over a hardware keyboard on an iPad, nothing on the game's screen; the view takes no touch, is nothing for VoiceOver, and throws away what a hardware keyboard types ([`CartoucheGuestControllers.m`](../../launcher/LiveProcessSupport/CartoucheGuestControllers.m)). A text field of the game's keeps the keyboard, and the game's process asks again, every two seconds, once nothing has it. As the scene resigns active, the game paused behind the console or Cartouche left, the view lets the keyboard go, and the controller drives the console again. The game's process also notes the last press of a controller's button that reached it (`controllerPress` in `GameMemory.plist`, [`CartoucheGuest.m`](../../launcher/LiveProcessSupport/CartoucheGuest.m)), and Cartouche's journal says once for each game, as the game pauses or ends, that the controller's presses reach the game, so that a player's report says whether the game had its controller.

This amends [decision 38](../decisions.md): Game Mode alone does not bring a game behind the console its controllers.

**Why.** Issue #230: with a DualSense, on an iPhone 17 and on an iPad Air M1, both with iOS 27.2 and Cartouche 0.13.1, the controller drove the console and hid the game's controls on screen, but the game that Play started never moved; started on nxnative's settings screen, the same game played with it, on both. Both ways start the game behind the console, in the same process. Play writes `DM_LAUNCHER=0`, and the game starts at once, without a touch; on the settings screen, the player touches its Play button, which gives the game's process the keyboard. Nothing in an nxnative game asks for it: its only text field is the one of a software keyboard, while a game asks for text (`front_ios.m`). Until then, the presses went to Cartouche, whose console takes none of them but Home while the game is on screen. LiveContainer issue 1587 says the same of its own windows: a game there gets nothing from its controllers until one of its text fields has had the keyboard. Asking for the keyboard is what a game with a text field does, with UIKit's public calls, in the game's own process, and LiveContainer's scene hosting already grants it, as it does to a text field (`_UISceneEventDeferringHostComponent` on iOS 27, `_UISceneHostingEventDeferringExtension` before). Passing the presses on from Cartouche to the game instead would have needed a channel of Cartouche's own for every button and stick of every controller, and nxnative reading it. Not yet tried on an iPhone: the launcher's harness checks the view in a scene of its own (`ControllerTests`), and the version's trial and the player's answer will say.
