# Showcase site

[`index.html`](index.html) is Cartouche's showcase page: one static page, in French, English, Spanish and German, that shows the app's screens rebuilt in HTML and CSS at their sizes in points, around nine games of nxnative's list, and says how to install Cartouche. It stays short: each section names what Cartouche does and links to its page in [the documentation for players](../docs-site/README.md), at <https://docs.cartouche.cloud/>, in the reader's language, which gives the details ([decision 161](../docs/decisions/161.md)). A visitor can move the console's focus, and send the game behind the console, then bring it back.

| Screen | Where the page shows it |
| --- | --- |
| The home, landscape on an iPhone 17 Pro (upright on a phone) | The top of the page |
| All games, with a controller connected | The console |
| A game's sheet and its settings, then the names of what else a sheet does: its description translated, Edit the game's info, a save from the console, Siri and the Home Screen, Share the log, Import my copy | A game's sheet |
| The game behind the console, paused or resumed | During a game |
| The System page, with the automation that renews Cartouche every night | Behind the scenes |
| Cartouche Cloud's page, on an iPhone linked to an account, past its credits: each game's cover, and the phases of a build under way | No Mac |

## What it may show

- **Games of nxnative's list, with their covers from IGDB, as in the app.** Each game on the page is one of [`catalog/nxnative.json`](../catalog/nxnative.json), with where nxnative plays it and the colours Cartouche gives it. Its cover and artwork are IGDB's, by the IDs of [`catalog/covers.json`](../catalog/covers.json), loaded from IGDB's image server as the app loads them ([docs/decisions.md](../docs/decisions.md), 22 and 40): the page itself holds no image of a game. Under each cover, the page draws the label Cartouche draws, which stays when an image cannot load (offline, or a preview that blocks other sites). The page credits IGDB, says the games belong to their publishers and that Cartouche provides none of them, and that play times and sizes are examples.
- **No game and no way to one.** No link to a game, a dump, an IPA, a catalog of games, keys or firmware: each player brings their own copy. The only downloads are the project's own programs for a computer, the Cartouche Installer for Mac and for Windows and Cartouche for Mac, each button giving the file itself from this repository's releases ([Downloads](#downloads)).
- **Pictures of its own, never a game's.** [`apple-touch-icon.png`](apple-touch-icon.png) is Cartouche's icon ([`app/icon`](../app/icon/)) at 180 × 180, for an iPhone or an iPad that puts the site on its Home Screen. [`social.png`](social.png), 1200 × 630, is what a link to the site shows where it is shared, on Discord, Reddit or in Messages (`og:image`): Cartouche's icon beside the page's title, drawn from [`tools/social.html`](tools/social.html). Each page names its own address at the domain (`canonical`, `og:url`), and the showcase page the address of each of its languages (`hreflang`, [Search engines](#search-engines)).
- **Nothing else third-party.** No font, script or analytics from another site, no cookie, no request but IGDB's images, sent without the page's address, and no address of a server of the project. The page links only to this repository, nxnative's, IGDB, nxnative-nobc, named as the separate fork of nxnative by mianmuhammadse that it is, as its author asked, and Cartouche's Discord server, by the one invite its bot keeps, `https://discord.gg/wG3DZjdAeF` ([decision 129](../docs/decisions/129.md)): in the header beside GitHub, in the footer and in the FAQ's answer on help, and in the download page's footer. It links to the documentation, at <https://docs.cartouche.cloud/>, in the language the visitor reads: from the header, the first screen, each section and the footers, each link to a page `docs-site/` has. It links to Cartouche Cloud's site too, its first page and its privacy notice, from its section and the FAQ, and to nothing else of it ([decision 138](../docs/decisions/138.md)): the page says what Cartouche Cloud does for a player with no Mac, never its price, which its own site and the app give. The tests fail on an amount of money on any page of the site.

[`tests/test_site.py`](tests/test_site.py) checks all of this: each game, its status, its cover and artwork and its colours against the catalog and the app, every text in French, English, Spanish and German, the pictures by their names and sizes, what a shared link shows, and the download page and the 404 page too; [`tests/test_downloads.py`](tests/test_downloads.py) checks the script that gives the downloads their newest release. CI runs it on every pull request (Showcase site); a catalog change that touches a game of the page fails it until the page's list follows.

## Search engines

The Showcase site workflow publishes the page once in each of its four languages, each at its own address, for search engines, which read a page by its address and in one language ([decision 175](../docs/decisions/175.md)): English at the root, <https://cartouche.cloud/>, French, Spanish and German at `/fr/`, `/es/` and `/de/`. [`tools/languages.py`](tools/languages.py) writes them from `index.html`, once the download links have their newest files: each page keeps its own language's texts alone, the screens the script draws aside, and has its title, its description and what a shared link shows in that language, from the `data-fr`, `data-en`, `data-es` and `data-de` of the head's `<title>` and `<meta>`. Each names its own address (`canonical`, `og:url`), its language (`og:locale`) and the four pages (`hreflang`, the English one for any other language, `x-default`), and says its language in `data-page-lang`: the script shows that one, the English page sends a visitor who reads French, Spanish or German, or chose one of them, on to their page at the same place, and the language buttons lead to the page in the language chosen. `index.html` as it is, served from `site/`, still changes its language in place. Its links to its icons and to the download page start from the site's root, `/`, so that they lead to the same files from each folder.

The title and the description name what players search for: Cartouche, the Switch games nxnative runs natively, iPhone, iPad and Mac, in each language; the page names Switch for what the games are, as the owner chose (2026-11-26). What search engines read of the app, in `<script type="application/ld+json">`, is the site and Cartouche as a free game application for iOS, iPadOS and macOS, with its description in the page's language, its documentation, its repository and its licence: never a price, an offer or a rating. [`robots.txt`](robots.txt) lets them read every page and names [`sitemap.xml`](sitemap.xml), which lists the four pages, each with the three others, and the download page. The tests write the four pages and check each of them.

The owner verified the domain in [Google Search Console](https://search.google.com/search-console), whose record is in [`domain/records.json`](../domain/records.json), and gives it the site's sitemap and the documentation's there ([domain/README.md](../domain/README.md#search-engines)).

## Working on it

```
python3 -m http.server -d site 8000        # then open http://localhost:8000
python3 -m unittest discover -s site/tests -v
```

The page has no build step: its styles, icons and script are inside it, and it uses the system's fonts. Each screen is a container whose sizes are numbers of points (`--pt`), so it is drawn as the app lays it out, at any width. The games are the list at the top of its script, `<script id="games">`: a game's title ID, name, platform, genre and where nxnative plays it as `catalog/nxnative.json` has them, its cover and artwork as `catalog/covers.json` has them, and its colours as `CartoucheTheme.colors(for:)` makes them from its title ID; the tests say what differs. [`favicon.svg`](favicon.svg) is the app's icon ([`app/icon/svg/light.svg`](../app/icon/svg/light.svg)) with the corners iOS gives it.

[`404.html`](404.html) is the page GitHub Pages serves for an address the site does not have, at any depth: its links and icons start from the site's root (`/`, `/download/`). To draw `social.png` again, from the repository's root, with Chrome (`--no-sandbox` as root in a container):

```
chromium --headless --hide-scrollbars --force-device-scale-factor=1 \
  --window-size=1200,630 --screenshot=site/social.png site/tools/social.html
```

## Downloads

Each download button links to the file itself, `Cartouche-Installer-<version>-Mac.dmg`, `Cartouche-Installer-<version>-Windows.exe` or `Cartouche-Builder-<version>.dmg` in its release, so that a click downloads it, with no stop on GitHub's releases. No address of GitHub's would stay the newest: GitHub's *latest* release is a single release of the three programs the repository publishes, Cartouche's `v<version>`, the Installer's `installer-v<version>` and the Builder's `builder-v<version>`, and each file's name carries its version. So the link is marked `data-download="<file>"`, and at each publication [`tools/downloads.py`](tools/downloads.py) gives it the newest release that has the file, by its version, as Cartouche Builder takes its own updates: neither a draft nor a pre-release, with its SHA-256 for the Builder and both files for the Installer. The page in the repository links to the versions it last saw; the published page, to the newest. The pages say no version, beside a button or anywhere else: a button says what it downloads, as the owner asked (2026-11-10), and the tests check it.

[`download/index.html`](download/index.html), at <https://cartouche.cloud/download/>, offers the same three files on a page of their own, for the repository's guides and anything else that links to them: a link that names one, `download/#installer-mac`, `download/#installer-windows` or `download/#builder`, downloads it at once, and the page stays with what to do next. A fourth card, `download/#sidestore`, gives the source for the player's own SideStore, its address and a button that adds it there ([decision 160](../docs/decisions/160.md)).

## Publishing

The page is on GitHub Pages since the owner said so (2026-11-10), at <https://cartouche.cloud/>, the project's domain, since 2026-11-17 ([domain/README.md](../domain/README.md)). When `site/` changes on main, the [Showcase site](../.github/workflows/site.yml) workflow runs these tests, gives the download links the newest releases, writes the page in each of its languages ([Search engines](#search-engines)), then keeps `index.html` and its French, Spanish and German pages in `fr/`, `es/` and `de/`, `download/index.html`, `404.html`, `favicon.svg`, `apple-touch-icon.png`, `social.png`, `robots.txt`, `sitemap.xml` and [`CNAME`](CNAME) alone on the branch `gh-pages`, in one commit made again at each publication, with a `.nojekyll` so that Pages serves them as they are. Beside them goes `sidestore.json`, Cartouche's source for the player's own SideStore, [`app/sidestore-player-source.json`](../app/sidestore-player-source.json) as main has it, at <https://cartouche.cloud/sidestore.json>, the address `app/config.env` gives the IPA for that SideStore: the workflow runs again whenever that file changes on main, as the Release workflow's *Source* pull request changes it, and the page shows the address players add, `https://source.cartouche.cloud`, in the install's second step and on the download page's card `#sidestore`, with a button whose link, `sidestore://source?url=https://source.cartouche.cloud`, has SideStore add it ([decision 155](../docs/decisions/155.md), [decision 160](../docs/decisions/160.md)). The workflow then deploys the Worker that answers with it at <https://source.cartouche.cloud/>, the address a player adds to their SideStore ([source/README.md](../source/README.md)). `CNAME` names the domain: Pages serves the site there, and sends its old address, `cartouche-app.github.io/Cartouche`, on to it, page by page. A publication without it would drop the domain while its records still point to GitHub Pages, so the tests check that each one keeps it. The Builder and Installer workflows run it again once they have published a release, so that the buttons give it within minutes. Pages serves that branch: **Settings › Pages › Build and deployment**, *Deploy from a branch*, `gh-pages`, `/ (root)`. Nothing else of the repository is published. To publish main's page again, run the workflow from the Actions tab.
